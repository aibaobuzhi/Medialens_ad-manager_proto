01｜执行摘要

先给结论，再看证据

首选
Adyen

官方明确覆盖 autonomous store、预授权、授权调额、手动捕获与失败追款。

最快商用
365 / Nayax

柜体、支付、设备与运营后台更完整，适合先验证商业模型，定制自由度较低。

开发者备选
Stripe

API 体验强，UX700 支持美国无人场景；但本用例的增量授权资格需书面确认。

核心风险
10×

$20 预授权扩到 $200 不是“补扣必成”；发卡行、卡种、MCC 与网络规则都可能拒绝。

建议：Adyen 主轨 + 365/Nayax 商业备援

用 Adyen 做可控支付底座 POC，保留自研 AI 识别、订单与设备编排；同时向 365/Nayax 索取整套设备报价与 SLA，作为缩短上市周期的对照组。不要把“捕获超过原授权额”设计成确定性能力。

Go / No-Go 前置条件：收单方必须书面确认美国无人零售 MCC、目标卡种、UX/终端型号、预授权、incremental authorization、tokenized card-on-file 补款、退款/争议与断网策略。任一项只靠销售口头承诺，均不进入量产。

03｜方案逐一拆解

准备工作、技术路径、优缺点与官方 use case

Adyen

Enterprise PSP · 推荐主轨

Pros

  • 官方 Autonomous Stores 直接命中用例
  • 预授权、同步/异步调额、捕获、webhook 完整
  • 可 token 化后追收差额
  • 多国扩展与统一对账能力强

Cons

  • 企业准入与商务周期可能较长
  • 终端、MCC、卡种限制需逐项配置
  • 柜控、CV、库存、客服均需自建

准备工作

  • 美国实体、银行账户、KYC/UBO、业务模型与交易预测
  • 申请 Terminal API、manual capture、smart pre-auth、authorization adjustment、webhooks
  • 选无人终端并完成远程联网、EMV/接触式/非接触式测试

官方 use case：Autonomous stores 明确说明刷卡进店、调额、捕获及失败补款。

Nayax

Unattended retail full stack · 快速落地备选

Pros

  • 支付、4G、遥测、设备与库存一体
  • 无人设备经验成熟，安装路径短
  • 美国在线商店可见硬件与部分费率
  • Selfly Store 有智能冰箱全球扩张案例

Cons

  • 交易费可能高于直接收单
  • API、数据导出、支付编排自由度需核实
  • 合同、设备订阅与平台锁定

准备工作

  • 确认 VPOS 型号、MDB/脉冲/串口接口与柜控兼容
  • 索取 API、webhook、multi-vend、预授权上限和 sandbox
  • 核对 SIM 覆盖、远程升级、RMA、结算周期与数据出口

官方 use case：Selfly Store × Nayax OEM。

Stripe

Developer-first PSP · 技术备选

Pros

  • API、sandbox、事件模型与开发体验成熟
  • 标准费率透明，无长期平台包袱
  • Terminal 与线上 token/PaymentIntent 体系统一
  • Connect 适合未来多商户平台化

Cons

  • 美国无人场景硬件当前集中于 UX700
  • incremental auth 并非所有交易都适用
  • IoT、库存、订单异常与客服工具自建
  • 必须向销售确认供货与 unattended 资格

准备工作

  • 联系 Stripe Sales 申请 UX700 与 unattended retail
  • 用真实 MCC/卡种验证 manual capture、incremental authorization 与 card-on-file
  • 建立 PaymentIntent、reader action、webhook 幂等与离线降级

官方说明：美国无人终端 UX700；正式 POC 前要求书面 capability matrix。

Cantaloupe

Smart retail operator platform · 成品方案对照

Pros

  • Smart Store、支付、Seed 管理平台一体
  • 补货、路线、库存与销售运营成熟
  • 官方案例披露销售提升与低 shrink
  • 适合多点位规模运营

Cons

  • 价格与 API 公开度有限
  • 自研 CV/柜体能力可能与成品栈重叠
  • 支付数据与体验定制受平台边界约束
  • 迁移成本高

准备工作

  • 按点位数、SKU、温控、尺寸与补货模型索取方案
  • 要求展示 API、原始交易/库存导出、告警与 SSO
  • 谈清硬件所有权、SaaS、处理费、安装、RMA 与解约迁移

官方 use case：Canteen of Northern California 披露单点周销售从 $450–600 到 $1,600。

365 Retail Markets

PicoCooler Vision full stack · 最快体验验证

Pros

  • AI 视觉、锁控、支付、柜体与后台现成
  • 官方清楚描述 pre-auth 与超额增量授权
  • 365Ops / ADM 支持库存与 planogram
  • 适合快速部署真实点位验证

Cons

  • 硬件与软件形态固定
  • 自有 AI 与数据资产差异化空间较小
  • 报价、支付费率和 API 需销售获取
  • 增额仍受发卡行与支付方式限制

准备工作

  • 索取 PicoCooler Vision demo、SKU 限制、识别指标与安装手册
  • 确认 pre-auth 默认额、incremental cap、失败追款与消费者收据
  • 验证原始图像/事件/订单数据出口与第三方系统 API

官方说明：PicoCooler Vision FAQ 明确说明超额时会尝试 incremental authorization，但结果依赖发卡行、支付类型及 cap。

04｜报价与合规

公开价只用于预算锚点，最终以美国正式合同为准

公开价格锚点

  • Stripe：美国线下国内卡标准价 2.7% + 5¢；UX700 需联系销售
  • Adyen：固定处理费 + payment method fee；美国终端/企业报价需询价
  • Nayax：美国商店示例 VPOS Touch $399（批量可降）；月费及 2.5%–5.95% 示例区间依方案计算
  • Cantaloupe / 365：整套方案询价

要求供应商拆分的 TCO

  • 终端/柜体采购或租赁、安装与物流
  • SaaS、SIM/流量、设备管理、API 费
  • 收单、网关、授权、调额、退款、拒付费
  • 最低承诺量、月最低费、跨境卡与钱包附加费
  • 备件、RMA、现场维护、提前解约与数据迁移

合规责任矩阵

  • PCI DSS：使用 P2PE/认证终端缩小范围；不得保存敏感认证数据
  • EMV / PCI PTS：只选认证终端与受支持固件
  • 卡组织规则：预授权文案、有效期、增额与及时捕获
  • 美国税务：按部署州/城市处理 sales tax 与免税商品
  • 隐私：摄像头告知、最小化留存、CCPA/州隐私法评估
  • 消费者：清晰展示 hold、最终扣款、数字收据与申诉渠道
报价基线建议：向五家发同一份 RFP：100 / 1,000 / 10,000 台三档；月均 600 笔/台；客单 $12；退款 1%；争议 0.3%；美国境内卡 90%；要求同时给出一次性、经常性、处理费、SLA 与五年退出成本。

05｜预授权 $20 → 最终 $200 异常流程

把“调额失败”设计为常态分支，而不是边缘异常

1$20 PreAuth读卡、风险检查、记录 PSP reference / token；失败则不开门。
2开门购物建立 session，绑定柜、卡别名、时间与 CV 事件。
3关门结算AI 生成 $200 篮子；订单先进入 calculating，禁止立即展示“支付成功”。
4调额至 $200请求 authorization adjustment / incremental auth；最多有限重试，不拆单撞库。
5A成功：捕获 $200等待 capture webhook，再出最终收据、释放 session。
5B失败：先保全 $20按 PSP 规则捕获原授权额；差额 $180 进入应收账。
6合规追款用已同意的 token/MIT 追收或发 payment link；失败则风控拦截下次开柜并转客服。

不能做

  • 不能直接 capture $200 并假设网络会接受
  • 不能无限次重复授权同一张卡
  • 不能在 webhook 未确认时写“已付款”
  • 不能因支付失败远程锁住已在柜外的商品或威胁消费者

产品防线

  • 将预授权额动态设为 SKU 风险、用户历史与库存价值的函数
  • 高价值柜使用 $50/$100 或逐级补授权
  • 支付卡种不支持调额时限制可取商品总额
  • 门上展示 hold 金额、释放时间与最终收费机制

账务状态机

preauth_pending → authorized → shopping → amount_calculated → adjusting → captured / partially_recovered / collection_pending / written_off

所有状态由 PSP webhook 驱动、幂等写入；CV 订单与支付账本分离但可审计关联。

06｜PRD 核心范围

POC 只做能决定方案成败的能力

用户故事与验收

  • 用户刷卡/钱包，3 秒目标内得到开门或明确拒绝
  • 关门后收到商品明细、hold 说明与最终电子收据
  • 错识别可在订单页提交申诉，后台保留事件证据
  • 调额失败时不误报成功，客服可见授权、捕获、差额与追款状态
  • 运营可远程查看终端、门锁、网络、相机与库存健康度

非功能指标

  • 支付/开门链路 P95 ≤ 3 秒；支付服务月可用性目标 ≥ 99.95%
  • 重复扣款 = 0；webhook 重放与断点恢复 100% 幂等
  • 订单金额识别准确率 ≥ 99%（先限定 SKU 与陈列）
  • 离线时默认不开新柜；已开 session 可安全关门并待恢复处理
  • 敏感日志脱敏；事件、订单、支付证据可追溯 ≥ 合同/法规要求

后台能力

  • 设备：在线、固件、信号、终端配对、远程重启
  • 订单：CV 明细、人工改判、退款、差额追收
  • 风控：卡别名 denylist、频率、金额、点位、设备风险
  • 对账：授权/调额/捕获/退款/拒付/结算逐笔核对
  • 告警：门未关、相机遮挡、捕获失败、库存漂移

POC 不做

  • 全美多州税务自动化、复杂促销与忠诚度
  • 所有钱包/EBT/FSA/HSA；先测 Visa/MC/Amex/Discover 与 Apple/Google Pay
  • 完全离线开柜
  • 多租户平台、白标结算与跨国部署
  • 未经验证的高价值/受监管商品

08｜决策建议

建议今日批准的事项

Decision 1

批准 Adyen 主 POC

以 Terminal API + 无人终端验证完整支付状态机；保留自研 CV、订单、风控与设备编排，最大化长期差异化与数据控制。

Decision 2

并行获取 365 / Nayax 报价

让成品方案提供上市时间与五年 TCO 基线；若 Adyen 商务准入、终端供货或调额资格未过 gate，可立即切换。

Decision 3

暂不承诺 $200 可收回

量产 PRD 采用“动态预授权 + 增额尝试 + token 合规追款 + 风险限额”，并为坏账、客服与争议预留预算。

GateGo 标准No-Go / 切换条件Owner
支付能力目标卡种调额与捕获在真实卡测试达到约定成功率；有书面支持矩阵只支持特定高风险 MCC 之外的场景，或无法 token 追款Payments / Legal
消费者体验P95 开门 ≤ 3s；hold 与最终金额清晰；申诉闭环hold 释放不可解释或错扣无法快速处理Product / CX
